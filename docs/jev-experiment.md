# Jev parsing and categorization experiment

The [Jev reference guide](jev-reference-guide.md) recommends code for exact parsing and arithmetic, Jev for choosing among supplied candidates, and a generative model when the needed value cannot be selected from candidates. The implemented parsing route follows that division: code parses unambiguous lines, Jev chooses among date or amount spans when multiple matches remain, and the subscription LLM receives unresolved lines. Jev's selection is checked against the original span and parsed by code. The `0.8` top-option probability threshold is provisional and needs calibration on labeled inputs.

The custom [expense parsing fixture](../packages/analyze-expenses-workflow/tests/fixtures/expense_parsing_experiment.txt) contains a clean transaction, a refund with two amounts, a purchase date plus posted date, a charge plus available balance, and an amount that is absent. The offline [cascade test](../packages/analyze-expenses-workflow/tests/integration/test_expense_parsing_cascade_experiment.py) verifies all three routes and leaves the truly missing amount unresolved. Code also leaves a balance-only monetary field unresolved and does not turn “no refund” into a credit. A regression case checks two identical dollar amounts: Jev's choice identifies the selected occurrence, so a selected balance cannot be treated as the charge. The LLM response currently supplies amount text without an occurrence position; if the same text also occurs as a balance, its answer remains unresolved. Opt-in live checks passed on 24 September 2026: Jev selected the refund amount and purchase date; the Codex fallback using `gpt-6-sol` with `medium` effort recovered the charge amount after Jev abstention; the Copilot fallback recovered it with `gpt-6-astra` and `claude-haiku-4.5`, both at `low` effort. The Claude response enclosed valid JSON in a Markdown fence, which the processor now accepts only when the fence wraps the whole response. Earlier exploratory `gpt-6-luna` responses did not reliably resolve that synthetic line. These few examples do not establish comparative accuracy.

The [repeatability probe](../packages/analyze-expenses-workflow/tests/integration/test_jev_category_repeatability_experiment.py) ran Jev three times on each of five transactions from the existing corpus. All 15 final categories agreed with each other and with the probe's expected policy labels. The grocery example's chosen-option probabilities were 0.65, 0.68, and 0.66 despite all three labels agreeing; the other four examples ranged from 0.94 to 1.0. This is a small stability check, not a held-out accuracy result. Some cases are forced by merchant or cash-movement policy after the Jev response. Repeating live categorization in production would add cost and latency; the current evidence gives no reason to do so. Before considering voting or a second call, use a larger labeled set with ambiguous neighboring categories, record raw category distributions, and compare automatic coverage and error rate against single-call Jev.

Other useful Jev trials from the guide are evidence-grounded verification of an LLM-extracted field and a narrow “is the spending purpose stated?” judgment for ambiguous transfers. Both need labeled examples and explicit acceptance rules before joining the production route. Totals, refund sign handling, duplicate confirmation, and reconciliation remain code-owned.

The selected SDK determines the model family: Codex and GitHub Copilot use OpenAI; Claude Code maps to Anthropic, but that SDK gateway is not yet implemented and cannot be selected at runtime. Operation settings select a model and reasoning effort within the SDK's family, such as `EXPENSE_LINE_EXTRACTION_OPENAI_MODEL` and `EXPENSE_LINE_EXTRACTION_OPENAI_REASONING_EFFORT`. Family override settings are rejected so they cannot disagree with the SDK. Known cross-family model IDs, including `claude-*` and `anthropic/*` in OpenAI settings, are rejected during configuration. Anthropic-specific model and effort keys are reserved for the future Claude Code gateway. Configuration rejects `none`, `minimal`, and `ultra` effort for Copilot, whose gateway accepts `low`, `medium`, `high`, `xhigh`, and `max`. `EXPENSE_CATEGORIZATION_*` settings are reserved for a possible LLM categorization fallback; current categorization still uses Jev. Exact model and effort availability must still be checked against the selected subscription backend.
